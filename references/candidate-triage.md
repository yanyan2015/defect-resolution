# 候选分档与闸门话术（阶段 3 速查）

## 分档判定表

对每个候选，按顺序问；第一条命中即定档：

| # | 问题 | 是 → |
|---|---|---|
| 1 | diff 只含空白/格式/注释/重命名搬运（`show -w` 为空、rename 检测命中）？ | **排除** |
| 2 | 改动文件全是文档/测试/CI/版本号/生成文件，不碰报错路径的产物代码？ | **排除** |
| 3 | diff 引入/删除/改写了报错信息里点名或 pickaxe 命中的符号、宏、调用、条件？ | **强候选** |
| 4 | 「已修复代码」的行 100% 在该 commit 出现、在父提交不出现？ | **强候选**（最强形态） |
| 5 | commit message / trailer / 新增测试明确对应报错关键词或 issue？ | **强候选** |
| 6 | 改动落在报错文件/函数邻近，但语义联系说不清？ | **弱候选** |
| 7 | diff 触碰报错路径但只是顺手清理（无符号增删、无条件变化）？ | **弱候选～排除** |

## 闸门前的自检

呈现候选表前，先对自己过一遍：

- **强候选是否唯一？** 唯一 → 闸门里推荐「直接验证该候选」。多个 → 给出区分建议（谁的 diff 离报错行更近、谁带测试、谁 message 明确）。
- **有没有漏掉 merge 带入的修复？** 对比 `RANGE_TOTAL` 与 `RANGE_NO_MERGES`；对 pickaxe 命中但不在 `--no-merges` 集合的提交跑 `show -m`。
- **「最新改动该路径的提交」是不是在冒充修复？** path-recent 是弱信号（权重 1），它经常排在表前列 purely because 时间近。用阶段 3 的规则降档它。
- **报错符号是否太泛？** `status`、`error` 这类符号的 pickaxe 命中一堆；回到报错原文找引号字面量级别的特异符号重跑 collect。

## 闸门话术（AskUserQuestion）

把候选按档呈现为表格后询问。选项设计：

1. **「按强候选验证」（推荐默认）** —— 正常路径。
2. **「调整候选集」** —— 用户可能知道：该报错后来在 issue 里被重新归因 / 某个 commit 是后续合入的 backport / 复现命令是什么。任何一条信息都能大幅收窄。
3. **「只做静态验证」** —— 用户环境没法构建/运行；阶段 4 跳过 --run-cmd，可信度封顶「中」。
4. **「强候选里再缩小」** —— 用户指认某一个或要求补充证据。

**用户给出复现命令时**：无条件把「真实 bisect」加入阶段 4 计划，并在闸门里说明预期耗时（取决于构建时间 × ⌈log₂(范围)⌉）。

## 强候选过多时的收窄顺序

1. 要求「已修复代码」文本（哪怕只有 3–5 行）→ 用 `collect.sh --fixed` 重跑，权重 5 的通道会立刻分出高下。
2. 用报错原文的**引号字面量**级符号重跑 pickaxe（`error: 'X' has no member 'y'` 的 `X`、`y`）。
3. 检查候选里是否有同主题系列提交（同一 issue 多个 commit）：它们要么合并为一个逻辑修复（取最后一个），要么 message 里已写明分工。
4. 仍无法区分 → 如实输出多候选结论（SKILL.md 阶段 6 的「未确定项」），并给一条区分建议。

## 反向归因：定位**引入**缺陷的 commit

同一套证据链换个方向用。用户在问"这个 bug 是哪个提交引入的"时：

1. **锚点对调**：问题版本 = 修复 commit 的父提交（`<fix>^`）；修复版本 = 出问题的那次发布/提交。
2. **阶段 2 直接给答案**：报错行的 blame 归属（在坏版本上算）就是引入者。`collect.sh` 的 `blame[issue-line]` 通道记录的就是"问题版本第 N 行归属该提交"。
3. **交叉验证**：
   - 方法 B 反过来做：看 `<fix>^` 相对 `<fix>^^` 多了什么 —— 那正是引入 bug 的 diff。
   - 方法 C 反过来：把引入者 revert 掉，报错应消失。
   - `git log -S'<符号>'` 找符号的引入点（注意区分"引入"与"修改"：`--diff-filter=A` 看新增文件、`-S` 看次数变化）。
4. **注意合并与回滚**：缺陷可能是被 **revert 引入**的（先修好、后被回滚）。此时引入者是一个 revert commit，用 `git log --grep='Revert' -S'<sym>'` 额外查一遍。

## 同一 bug 的多个修复（backport 场景）

开源项目里同一个 bug 常有**两个修复 commit**：

```
main         (开发)     ──────┬───────► v3.0.0
                          fix!         ← 原始修复
X.Y-stable  (维护)     ───fix!──► v2.9.1   ← cherry-pick 的 backport
```

识别方法：

```bash
git branch -a --contains <fix>              # 这个修复在哪些分支上
git log --all --oneline --cherry-pick --left-right <main>...<stable>
git log --all --oneline --grep='backport' -S'<符号>'
git log --all --oneline --grep='#<issue 号>'
```

处理方式：**不要强行择一**。给出两个候选，各自标明：

| 候选 | 所属分支 | 首次包含的发布版本 | 适用人群 |
|---|---|---|---|
| `aaa1111` | main | v3.0.0 | 用主干的用户 |
| `bbb2222` | 2.9-stable | v2.9.1 | 还在 2.9 分支的用户 |

并明确回答「**你该升到哪个版本**」—— 通常是用户当前分支上第一个包含修复的版本。

另外两种情况：

- **修复只在维护分支**：结论要点明「升级到主干最新版并不能解决你的问题，需升级到 vX.Y.Z」。
- **修复只在主干、维护分支没有**：结论要点明「维护分支的用户暂时无解，需等 backport 或自行 cherry-pick」。

## 输出前的最后一致性检查

- 结论里的 hash、行号、issue 号，每一个都能指回一条实际命令的输出？
- 可信度等级与验证矩阵（references/verification.md）一致？
- 「未确定项」没有藏住任何无法验证的断言？
- 反事实自检（阶段 5）做过了吗 —— 只回退那一行，报错必然重现吗？
