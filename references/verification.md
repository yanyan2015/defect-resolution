# 验证方法与判据设计（阶段 4 速查）

四种方法强度不同、证明的方向也不同 —— 它们**互补而非互替**：

| 方法 | 证明什么 | 不证明什么 | 强度 |
|---|---|---|---|
| A 真实 bisect | 该 commit 是首个使报错消失的提交 | 报错为什么消失（机制） | ★★★ |
| B 父提交对比 | 触发条件在该 commit 处被改变 | 改动是否就是用户报的那个报错的修复 | ★★ |
| C 反向验证 | 移除该 commit 报错形态重现 | 无（这几乎是最强的反事实） | ★★★ |
| D 版本归属 | 哪个发布版本首次包含该修复 | 那个版本的用户是否真的不报错了 | ★★ |

理想证据链：B 定位机制 + D 定位版本 + （A 或 C）坐实唯一性 → 可信度「高」。

## 方法 A：真实 bisect

前提：一条把「报错触发条件是否仍成立」变成**退出码**的命令。

约定（git bisect 语义，方向不能反）：判据在「报错仍会出现」的版本上必须以 `0` 退出，在「报错已消失」的版本上以 `1–127` 退出 —— 这样 first bad commit 才等于「首个让报错消失的提交」。
### 判据命令设计

（承接上面的约定：判据 = 「报错触发条件仍成立」→ 0；「已消失」→ 1–127。）

**报错是编译期**（最常见）：

```bash
# 报错 = 编译失败本身 → 编译失败（非 0）即 bad，天然满足约定
--run-cmd 'make foo.o >/dev/null 2>&1'

# 报错 = 编译日志中的特定错误 → 该错误文本还在 → 0（bad）
--run-cmd 'make foo.o 2>&1 | grep -q "error: .FOO_H. undeclared"'
```

**报错是运行期**：

```bash
# 报错文本出现 → 0（bad）；消失 → 非 0（good）
--run-cmd './prog 2>&1 | grep -q "segmentation fault"'

# 崩溃即 bad（139 = SIGSEGV）→ 天然满足（崩溃时退出码非 0）
--run-cmd './test_foo'
```

**报错是静态属性**（最快、最稳，首选）：

```bash
# 危险的无界调用还在 → 0（bad）
--run-cmd 'grep -q "strcpy(dst, src)" src/foo.c'
# "缺失的宏"还没补上 → 0（bad）
--run-cmd '! grep -q "define FOO_H" include/foo.h'
```

静态属性判据的局限：它验证的是「触发条件存在」，不是「报错真的消失」。只要修复 diff 极小、且报错与该内容强绑定（宏缺失→编译错），这是可接受的近似；结论里注明。

### bisect 工程细节

- `verify.sh` 在**临时 worktree** 里跑，不碰用户工作区；blobless clone 首次 checkout 可能触发批量 blob 下载，耐心等待或换 `--full`。
- 构建型判据要确保中间产物不跨 commit 污染：判据命令里先 `make clean` 或用独立构建目录（`make O=/tmp/bisect-build`）。**污染是 bisect 假阴/假阳的头号来源。**
- 单步运行太慢（>2 分钟）时：先试静态属性判据；不行就二分**手动**做（每次 checkout 后只跑必要子集），或缩小 bisect 区间（`git bisect start B A -- path/`，限定只二分触碰过该路径的提交）。
- flaky 判据（偶发失败）会让 bisect 乱跳：跑 3 次取多数，或对不可复现报错直接放弃方法 A，用 B+C。
- `git bisect log` 可以把过程存档贴进结论，作为证据的一部分。

## 方法 B：父提交对比

```bash
git -C $REPO show <cand>^:<file> > /tmp/parent.c
git -C $REPO show <cand>:<file>  > /tmp/fixed.c
diff -u /tmp/parent.c /tmp/fixed.c
```

要建立的因果三段论：

1. 父提交中，报错触发条件**成立**（缺失的宏不存在 / 错误的条件为真 / 缺失的判空）。
2. 候选提交中，该条件**不再成立**（diff 恰好消除了它）。
3. 该条件与报错信息的**词汇/符号完全对应**（报错说 `'FOO_H' undeclared`，diff 里就有 `+#define FOO_H`）。

三条都成立 → B 通过。第 3 条对不上时（diff 相关但报错词汇不匹配）→ B 至多算「弱通过」，可信度封顶「中」。

merge 提交：`show -m --first-parent` 展开后对比 `<merge>^1:<file>`（主线侧）。若修复在 merge 的**第二父侧分支**上已存在，真正的修复 commit 在该分支历史里，用 `git log -S <sym> <merge>^1..<merge>^2` 找到它。

## 方法 C：反向验证

```bash
git worktree add --detach /tmp/wt B        # 基于修复版本
cd /tmp/wt && git revert --no-commit <cand>
# 检查 1：revert 是否干净（不干净 → 后续提交在同一区域继续改过，以 B 为准）
# 检查 2：报错形态是否重建（符号回到父提交状态；判据命令重新满足 → 退出 0）
git -C $REPO worktree remove --force /tmp/wt
```

- revert 后**必须**检查报错形态是否真的回来了，而不是只看 revert 成功 —— revert 成功只说明 patch 可逆向应用。
- 判据命令与 bisect 用**同一约定**（触发条件仍在 → 0）：revert 应让触发条件重建，所以回滚后判据命令退出 0 = pass。若你的命令是「复现命令：报错重现 → 非 0」的约定，解读需反转并人工复核。
- 若候选 commit 同时含修复与无关改动，revert 会把无关改动一并回滚 —— 此时结论要注明「反向验证针对整个 commit」。
- 问题版本早于候选（revert 方向反过来）：在问题版本上 `cherry-pick -n <cand>`，检查报错形态是否消失。

## 验证矩阵 → 可信度

| B | D 版本归属 | A 真实 | C | 结论可信度 |
|---|---|---|---|---|
| 通过 | 通过 | 通过（first bad = 候选） | — | **高** |
| 通过 | 通过 | — | 通过（形态重建） | **高** |
| 通过 | 通过 | 静态区间扫描无更早等价修复 | — | 中～高（注明未运行） |
| 通过 | 无 tag（仓库无发布标签） | — | — | 中（注明无法给出发布版本） |
| 通过 | 通过 | — | — | 中 |
| 弱通过 | — | — | — | 中（注明机制关联不闭合） |
| 不通过 / 无法验证 | — | — | — | 低，或回到阶段 2 重找 |

## 方法 D：版本归属

回答"这个 bug 在哪个版本修好的"。完整说明见 `version-attribution.md`，要点：

- **不能用 `git describe --tags --abbrev=0`** —— 它给的是最近的上游 tag，修复落在两个 tag 之间时会给错（返回那个还带着 bug 的版本）。
- 正确算法：遍历所有 tag，用 `git merge-base --is-ancestor <fix> <tag>^{commit}` 判断是否已包含，取**最早**的那个。
- 同时给出「上一个仍含缺陷的版本」—— 用户往往更需要这个（告诉你该升到哪个版本）。
- 补充 `git branch -a --contains <fix>`：如果修复只在维护分支，结论里要点明"升级到主干最新版并不能解决"。

## 何时「无法验证」也要写下来

无法构建（缺依赖、平台不兼容）、报错不可稳定复现、仓库历史不完整 —— 这些都必须原样写进结论的「未确定项」，并给出补验路径（例如「在 Linux 环境跑 verify.sh --run-cmd 'make'」）。宁可结论可置信度低、不可验证项明确，也不要给出看似完整实则推测的结论。
